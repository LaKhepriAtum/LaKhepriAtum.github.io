## 한 줄 요약

에이전트가 과거 작업에서 뽑아 둔 교훈은 틀릴 수 있는데, 보통은 교훈만 전달되어 에이전트가 확인할 방법이 없습니다. WikiTrace는 교훈마다 그것이 나온 실행 기록을 링크로 붙여 두고, 의심스러울 때 에이전트가 직접 열어 보게 합니다. 다섯 개 벤치마크에서 평균 점수가 올랐고, 메모리 때문에 원래 풀던 과제를 틀리는 비율도 줄었습니다.

## 배경: 어떤 문제를 풀려는가

에이전트 메모리는 대개 과거 실행 기록을 짧은 교훈으로 압축해 다음 과제에 넣어 주는 방식입니다. 그런데 메모리가 항상 도움이 되지는 않습니다. 메모리 없이는 풀던 과제를 메모리를 넣자 틀리는 경우가 생기는데, 논문은 이를 메모리 유발 성능 저하(memory-induced degradation)라고 부릅니다.

저자들은 메모리 없이 세 번 모두 성공했지만 메모리를 넣자 실패한 과제를 분석했습니다. 그 실패의 52%가 에이전트가 따른 메모리 항목에서 비롯됐고, 가장 흔한 원인은 교훈 자체가 틀린 경우(20%)였습니다(3.2절).

원인은 두 가지로 정리됩니다. 교훈이 성공/실패 라벨만 보고 추론한 결과라 틀릴 수 있고, 근거가 된 실행 기록 없이 전달되어 검증할 수 없다는 점입니다. 평균 점수는 이 현상을 가리기 때문에 논문은 지표를 둘로 나눕니다.

- **개선율(Gain)**: 메모리 없이 실패하던 과제가 성공으로 바뀔 확률
- **회귀율(Regression)**: 메모리 없이 성공하던 과제가 실패로 바뀔 확률

## 핵심 아이디어

메모리를 세 층으로 쌓고 층 사이를 링크로 잇습니다.

1. **원본 실행 기록**: 손대지 않고 그대로 보관합니다.
2. **컴필레이션**: 실행마다 핵심 결정을 요약하고, 실패한 실행이면 원인 추정을 함께 적습니다.
3. **인사이트**: 실행 하나에서 최대 세 개를 뽑습니다. 한번 만든 인사이트는 수정하거나 지우지 않고, 서로 충돌하면 에이전트가 판단하게 둡니다.

각 인사이트는 자신이 나온 컴필레이션과 원본 기록을 가리킵니다. 새 과제가 오면 에이전트는 모든 인사이트를 첫 메시지로 받고, 가장 비슷한 과거 실행 세 개의 인사이트 ID와 링크된 파일의 읽기 권한도 함께 받습니다.

에이전트는 다음 상황에서 터미널 도구로 원본까지 내려가 확인합니다.

- 인사이트에 필요한 세부 정보가 빠져 있을 때
- 인사이트가 실패한 실행에서 나왔을 때
- 다른 인사이트와 충돌할 때
- 시도한 행동이 막혔을 때

별도의 검색 단계나 자동 검증기는 없습니다. 근거를 열어 볼 수 있는 길만 터 주고 판단은 에이전트에게 맡기는 설계입니다.

## 실험 결과

ALFWorld, ScienceWorld, PlanCraft, τ³-bench Retail, AppWorld의 여덟 개 스위트에서 평가했고, 에이전트 모델은 deepseek-v4-flash입니다(4.1절). 비교 대상 중 Insights Only는 WikiTrace와 같은 인사이트를 쓰되 원본 접근만 뺀 조건입니다.

| 방법 | 평균 점수 (표 1) |
|---|---|
| 메모리 없음 | 79.5 |
| ExpeL | 80.3 |
| AWM | 81.6 |
| ReasoningBank | 81.7 |
| Insights Only | 87.0 |
| **WikiTrace** | **90.2** |

- τ³-bench Retail에서는 Insights Only(85.1)가 메모리 없음(86.8)보다 낮았고, WikiTrace(88.2)는 이를 넘었습니다. 메모리 방식 가운데 모든 스위트에서 메모리 없음 이상을 기록한 것은 WikiTrace뿐입니다.
- 회귀율은 WikiTrace 4.5%, Insights Only 6.5%입니다. 메모리 없이 다시 돌리기만 해도 결과가 뒤집히는 비율은 9.7%였습니다(4.3절).
- 에이전트가 원본까지 내려간 비율은 쉬운 과제에서 22%, 어려운 과제에서 44%였습니다(5.1절). 내려간 실행의 43%에서 계획이 바뀌었습니다(5.2절).
- 테스트 시 비용은 Insights Only의 1.17배입니다(5.4절).

## 한계

저자들이 밝힌 한계는 다음과 같습니다.

- 메모리를 성공/실패 라벨만으로 만들기 때문에 컴필레이션과 인사이트 자체가 틀릴 수 있습니다. 링크는 확인할 길을 열어 줄 뿐 인사이트를 검증해 주지는 않습니다.
- 모든 인사이트를 첫 메시지에 넣으므로 메모리가 커지면 프롬프트도 커집니다. 프롬프트에 다 들어가지 않는 규모에서 필요한 검색 방식은 다루지 않았습니다.
- 실패 원인 분류는 에이전트의 추론 기록을 읽은 LLM 판정자가 붙인 것이라, 실제 원인과 다를 수 있습니다.

읽으면서 보인 주의점도 있습니다. 주 실험은 모델 하나를 중심으로 했고, 다른 모델(GLM-5.3-flash)로는 두 개 벤치마크만 확인했습니다. 더 큰 모델이나 다른 에이전트 구조에서도 같은 폭의 이득이 나오는지는 따로 확인이 필요합니다.

## 실무에서 가져갈 점

- **요약할 때 원본을 버리지 마세요.** 교훈만 남기고 로그를 지우면 나중에 그 교훈이 틀렸는지 확인할 방법이 사라집니다. 교훈에 원본 위치를 함께 저장하는 것만으로도 시작할 수 있습니다.
- **평균 성공률만 보지 마세요.** 메모리를 붙인 뒤 새로 깨진 과제를 따로 세어야 메모리의 부작용이 보입니다.
- **검증은 필요할 때만 하게 하세요.** 매번 원본을 읽히지 않고 의심스러울 때만 열어 보게 하면 비용 증가를 작게 유지할 수 있습니다.
